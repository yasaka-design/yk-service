  # 設計変更の履歴・理由

## 認証まわり(2026-08)

公開前のセキュリティ対応として、アクセス制御の方針を決めた。

### 前提となる要望
- 閲覧のみの人は**ユーザー管理したくない**(アカウント登録・ID発行なし)
- 書き込み(日報入力・目標設定)をする人は限定したい(現在3名: kondo@volvo-yasaka.co.jp / s.kurume@roadcar.jp / roadcar1967@gmail.com)
- 「人数が増えるたびに登録」は非現実的

### 決めたこと

**閲覧: 日付署名付きの共有リンク方式**
- 書き込みログイン後の画面で「今日の閲覧リンク」を発行できる
- リンクには発行日が署名付きで埋め込まれ、**発行から3日で失効**
- リンクを開いた時点のCookieに発行日が記録され、**それ以降に入力されたデータは常に見えない**(古いリンクが漏れても最新データは見られない)
- Supabase側のアカウントは一切使わない(anonキーで読み取りのみ許可)

**書き込み: メールアドレス + Authenticator(TOTP)6桁コード**
- パスワードなし。合言葉(固定パスフレーズ)方式は「漏れたら終わり」なので不採用
- 一度は「メールにワンタイムコードを送る」方式(Resend経由)を検討したが、送信ドメインの認証(DNS設定)が必要でハードルが高く、断念
- 最終的にGoogle Authenticator等のTOTPアプリで6桁コードを生成する方式に変更。メール送信の仕組み自体が不要になった
- ログイン試行は3回失敗で15分ロック(メールアドレスごと、サーバーのメモリ上で管理。複数インスタンスに水平スケールする場合はこの仕組みは効かないので、その場合は共有ストアに置き換えが必要)

**Supabase RLS: サーバー専用アカウントで書き込みを分離**
- 当初はSupabaseのanonキーをサーバー・クライアント問わず共通で使っていたが、これだと「anonキーを知っていれば誰でも読み書きできる」状態だった
- service_roleキーの使用は要望により不採用(「role使いたくない」)
- 代わりに、**人間は使わないサーバー専用のSupabaseアカウント**(`SUPABASE_WRITER_EMAIL`/`SUPABASE_WRITER_PASSWORD`)を1つ作成
- RLSポリシーを変更: `anon`ロールはSELECTのみ、`authenticated`ロールのみ書き込み(INSERT/UPDATE/DELETE)可能
- アプリ側は、TOTPログインが成功した書き込みリクエストのときだけ、このサーバー専用アカウントでSupabaseにサインインしてから書き込む(`lib/supabase.ts`の`getWriterClient()`)
- 3人の人間それぞれのSupabaseアカウントは作らない(区別はうちのアプリのTOTPだけで行う。Supabase側からは「誰が書いたか」は区別できない設計)

### 副作用として直したこと
- クライアント側から直接Supabaseを呼んでいた箇所(`app/page.tsx`など)を、全部Next.jsのAPI経由に統一
- `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY`(ブラウザに公開される変数)を、`SUPABASE_URL`/`SUPABASE_ANON_KEY`(サーバー専用)に変更
